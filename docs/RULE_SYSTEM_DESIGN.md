# POCT 翻译工具：规则系统设计

> 目标：把“该不该翻、保留是否合理、算不算错”从散落在代码里的正则和词表，变成一套有数据源、有记录、有反馈出口的规则系统。改一条规则时，能预先知道它会影响哪些已知样本。

## 1. 现状：为什么总是修一个冒一个

### 1.1 同一个问题，由五个互不通气的地方各自回答

| 环节 | “这段该保留吗”的依据 | 位置 |
| --- | --- | --- |
| 翻译提示词 | 自然语言规则，如“把 Room/Building/Street 翻掉，只保留专有名” | `utils/translationProfiles.ts:49` |
| 翻译前保护 | 保护词表 + UUID/型号正则，替换成占位符 | `utils/translationTokens.ts:216` |
| 模型本身 | 自己判断，结果不告诉我们 | — |
| 规则质检 | 只看译文“像不像目标语言”，加语言 profile 词表、空格正则 | `quality/checks.ts`、`utils/language.ts:648` |
| AI 审核 | 另一套提示词，且写死“从中文原文翻译” | `services/sampleReviewAuditService.ts:90` |

五方各有一套判断，没有共同的来源。模型按提示词合理地保留了，质检用另一套标准判它错，“重译问题项”再把它送回模型，模型还是保留，于是死循环。

### 1.2 关键信息在流水线中途丢了

翻译前的保护步骤其实**知道**哪些片段是有意保留的（它把它们换成了占位符），但还原后这个信息就被丢掉了。质检拿到的只是一串纯文本，只能靠启发式重新去猜“这段英文是残留还是有意保留”。猜错一类，就加一条正则或词表；加的正则又误伤另一类。

### 1.3 同一个概念定义了多份

| 概念 | 定义份数 |
| --- | --- |
| 锁定列名 `LOCKED_KEY_REGEX` | 4 份（checks、language、translatorShared、agent） |
| `shouldLockCell` | 3 份 |
| 中文字符正则 | 9 处 |
| 血球代码正则 | 7 处 |
| 残留判断 | Excel 用 `detectUntranslatedCells`，DOCX/PDF 用 `runQualityChecksOnUnits`，口径不同 |

此外，`postprocess.ts` 里有 137 处 `replace`，`checks.ts` 里有 `connectthe|intothe|displaywbc…` 这类针对单个样本的硬编码。每一处都修好了当时的样本，但没有机制保证它不误伤其他样本。

### 1.4 判定只有“错”和“没错”两档，没有“确认无误”

一条误报一旦出现，用户没有办法关掉它，它会在每次质检和每次重译时反复出现。

**结论**：问题不在某条规则写得不好，而在于缺少三样东西：**统一的规则来源**、**贯穿全流程的片段标注**、**人工确认的出口**。

## 2. 设计原则

1. **一个规则来源，多个执行者。** 提示词、翻译前保护、质检、AI 审核都从同一份策略生成或读取，不再各写一套。
2. **记住决定，而不是事后去猜。** 翻译前就给每个片段打上类别，类别一路带到质检和报告。质检检查的是“这个片段是否按它的类别被正确处理”，而不是“这段文字像不像法语”。
3. **保留要有理由。** 模型保留的内容必须能对应到一个允许保留的类别，否则才算可疑。
4. **判定分级，每一级对应确定的动作。** 什么阻断交付、什么触发重译、什么只需人工确认一次，要事先约定。
5. **人工确认会被沉淀。** 用户点一次“确认无误”，就成为一条规则或例外，下次不再报，并自动生成回归样本。
6. **用误报率衡量规则。** 每次改规则都跑同一套样本库，同时看漏报和误报两个数，变好变坏一目了然。

## 3. 核心模型：片段类别（Span Category）

把一段原文拆成若干片段，每个片段归入下列类别之一。类别决定它的处理方式和质检口径。

| 类别 | 例子 | 翻译时 | 质检时 |
| --- | --- | --- | --- |
| `LOCKED` 锁定 | 占位符、UUID、型号 `EHBT-75`、血球代码 `WBC`、单位、数值范围、标准号 `EN 61010-1:2010`、URL、邮箱、电话 | 换成占位符，模型看不到 | 必须逐字一致，否则为**错误** |
| `ENTITY` 法定实体 | 公司法定名称 `Hunan Ehome Health Technology Co., Ltd.`、`Riomavix S.L.`、商标 | 按策略：保持原文，或使用登记过的官方译名 | 必须等于原文或登记译名，否则为**错误** |
| `PROPER` 专有名 | 地名 `Changsha`、园区名 `Liandong U Valley`、人名、物种拉丁名 | 允许保留原文或音译 | 两种都放行，只检查**全文一致** |
| `FIXED` 固定表达 | `Rx only`、`IVD`、`CE`、`EC REP`、`e.g.`、`Made in China`（按项目策略） | 按项目词表：保留原文或使用固定译法 | 必须等于原文或固定译法 |
| `PROSE` 普通文本 | 句子、标签、按钮名、地址中的 Room/Street | 必须翻译 | 检查目标语言、术语、格式 |

几点说明：

- **地址是混合体**：`Room 301, No.3 Building, Yulian Road, Changsha` 拆开是 `PROSE(Room) + LOCKED(301) + PROSE(Building) + PROPER(Yulian) + PROSE(Road) + PROPER(Changsha)`。整段保留还是半翻，由项目策略决定（见第 7 节），但质检不再需要猜。
- **类别来源有三个，按优先级合并**：
  1. 词库：`language-packs/` 下的 CSV（不翻译清单、术语表），加上用户在界面添加的保护词；
  2. 识别器：公司后缀（Co., Ltd./S.L./GmbH/B.V./Inc.）、地址关键词、邮箱、URL、电话、标准号、型号等模式；
  3. 模型自报（见 4.3）。
- **识别器只负责提出候选，最终类别以词库和策略为准。** 这样可以避免识别器变成新一批正则补丁。

## 4. 流水线改造

```text
原文
  │ ① 片段标注（Span Annotator）: 词库 + 识别器 → SpanMap
  ▼
带占位符的原文 + SpanMap
  │ ② 提示词：由同一份策略生成；告诉模型哪些类别可保留
  ▼
模型输出：译文 + kept[]（模型自报保留了哪些片段及原因）
  │ ③ 后处理：只做与类别相关的格式修复
  ▼
译文 + SpanMap（类别信息没有丢）
  │ ④ 质检：按片段类别逐项判定 → Finding(级别, 类别, 原因)
  ▼
  │ ⑤ 例外库过滤：已确认的项不再报
  ▼
报告 → 用户：确认无误 / 修正 / 重译
  │ ⑥ 反馈沉淀：例外库、词库、翻译记忆、回归样本
```

### 4.1 片段标注（新增 `rules/spanAnnotator.ts`）

- 输入：原文和目标语言；输出：`SpanMap = [{start, end, text, category, source: 'lexicon'|'detector'|'model'|'user', ruleId}]`。
- 由现有 `guardTranslationTokens` 演化而来：它已经在识别保护片段，只是没有保存结果。
- Excel、DOCX、PDF、字符串资源、本地 Agent 都调用同一个入口。

### 4.2 提示词从策略生成

- `translationProfiles.ts` 不再手写“地址怎么处理”这类规则，改为从策略渲染出来，例如“类别为 PROPER 的片段可保留原文；类别为 ENTITY 的片段必须原样保留或使用以下官方译名”。
- AI 审核的提示词使用同一段渲染文本，并去掉“从中文原文”的硬编码，改为传入检测到的源语言。

### 4.3 让模型说明保留了什么

翻译接口已经使用 JSON 包装（`__poct_record_id` / `payload`），在其中增加一个可选字段：

```json
{"__poct_record_id": 12, "payload": {...}, "kept": [{"text": "Liandong U Valley", "reason": "proper_name"}]}
```

- 自报的保留片段若属于允许保留的类别：放行，记为信息级。
- 若不在任何允许类别中：记为“待确认”，不直接判错，也不自动重译。
- 模型没有自报、但译文与原文一致的片段：交给识别器判断类别；识别不出来再按普通文本检查。

### 4.4 质检按类别判定（重构 `quality/checks.ts`）

现有检查项保留，但每一项都要先过一遍片段类别：

- 非目标语言残留：只检查 `PROSE` 片段。`LOCKED`、`ENTITY`、`PROPER`、`FIXED` 片段先剥离。这一条同时解决中文目标下保留英文公司名、俄语目标下保留拉丁地名的误报。
- 中文残留：与上一条同一入口，不再单独实现。
- 格式和空格检查：跳过 `LOCKED`、`ENTITY` 片段（`S.L.`、`No.13`、邮箱、网址）；语言相关的标点规则（如法语冒号前空格）放进语言 profile；原文本身就有的格式不算译文的错。
- Excel 的 `detectUntranslatedCells` 改为调用同一个核心，统一口径。

## 5. 判定分级与对应动作

| 级别 | 含义 | 例子 | 系统动作 |
| --- | --- | --- | --- |
| **错误** | 交付前必须处理 | 占位符损坏、锁定片段被改、法定名被改、普通文本整段未翻 | 阻断“可交付”状态，可自动重译 |
| **警告** | 很可能有问题 | 普通文本中夹杂源语言词、术语不一致、重音缺失 | 进入重译候选，由用户决定是否重译 |
| **待确认** | 系统无法判断 | 模型保留了一个无法归类的片段 | 不重译；用户确认一次后沉淀为规则 |
| **信息** | 合理的保留 | 地名、公司名按策略保留 | 只在报告中统计，不打扰用户 |

重译收敛规则：

- 只有**错误**会自动重译，**警告**需要用户选择后才重译。
- 同一片段连续两次重译结果相同，就停止重译，并降级为“待确认”。这样可以从机制上消除死循环。

## 6. 例外库与反馈沉淀

报告里每条 finding 增加三个操作：

1. **确认无误**：写入例外库，键为 `(规则ID, 原文片段, 目标语言)`，作用范围可选：本文件 / 本项目 / 全局。
2. **加入不翻译清单**：写入词库（即现有的运行时保护词，升级为带类别的词条）。
3. **修正并保存**：使用现有的“保存并应用”，同时写入翻译记忆。

每一次操作都自动导出为一条回归样本（复用现有的 `regressionAssets.ts` 和 `fixtures/translation-issue-regression.jsonl`）。这正是 `AGENTS.md` 中“每次发现问题都要沉淀”的要求，只是由界面操作自动完成，不再依赖人工记得去做。

## 7. 需要你定的策略（每个项目可配置，以下是建议默认值）

| 内容 | 建议默认 | 理由 |
| --- | --- | --- |
| 公司法定名称（制造商、欧代） | 保持原文，或使用登记过的官方译名 | 法规文件要求与注册信息一致 |
| 制造商 / 欧代地址整块 | **允许整段保留原文，也允许翻译**；只要求全文一致 | 注册证上的地址通常是英文原文，强制翻译反而有风险 |
| 正文中出现的普通地址 | 通用词翻译，专有名保留 | 与现有提示词一致 |
| 地名、园区名、人名 | 保留或音译都放行 | 质检无法判断哪种更好 |
| 固定表达（Rx only、Made in China、EC REP 等） | 按项目词表逐条决定 | 不同市场习惯不同 |

如果选择“允许整段保留”，需要把 `translationProfiles.ts:49` 的提示词同步改掉。在新设计里这一步是自动的，因为提示词由策略生成。

## 8. 防止“改完又出新问题”的机制

1. **样本库 = 已知正确答案，按类别而不是按文件建。** `fixtures/rule-golden.jsonl` 测的是规则类别（公司名、地址块、联系方式、锁定代码、固定表达、未翻译句子、占位符损坏……），每条标注期望判定。维护方式：
   - **模板生成**：用“类别 × 12 种目标语言”的模板一次性生成种子样本，之后基本不改。
   - **自动沉淀**：用户在报告中点“确认无误”或“修正并保存”时，自动追加一条样本，并按模式去重。用户不需要另外录入。
   - **真实文件只做差异对比，不做标注**：改规则前后各跑一遍最近翻译过的文件，只列出判定结果变化的条目，供人工扫一眼。
2. **每次改规则都输出两个数**：漏报（应报未报）和误报（不应报却报了）。`npm test` 中任何一个数变差即失败，并列出变化的样本。
3. **规则带 ID 和来源。** 每个 finding 写明是哪条规则（ruleId）、依据哪个词库条目或识别器，便于定位“是谁误伤了”。
4. **禁止单样本硬编码。** 新规则必须写成类别、词库或语言 profile 条目；`connectthe` 这类硬编码逐步迁移进样本库，验证无影响后删除。

## 9. 落地顺序（每一步都可单独验证、可回退）

| 阶段 | 内容 | 用户可见的变化 |
| --- | --- | --- |
| 0 | 建立样本库和误报/漏报指标，先度量现状 | 无；得到一份现状基线 |
| 1 | 合并重复定义，抽出 `rules/` 共用模块；Excel 与 DOCX/PDF 口径统一 | 无行为变化，基线数不变 |
| 2 | 片段标注 + 质检按类别判定 | 公司名、地址、邮箱、`S.L.` 等误报消失 |
| 3 | 判定分级 + 重译收敛 + “确认无误”按钮和例外库 | 不再死循环；误报可一键关闭 |
| 4 | 提示词和 AI 审核改为由策略生成；模型自报 `kept[]` | 三方口径一致，AI 审核不再误报 |
| 5 | 把历史硬编码迁移进样本库后清理 | 代码变少，行为不变 |

阶段 0 和阶段 1 不改变任何行为，只是让后面的改动可度量。建议从这两步开始。

## 11. v0.3.2：松紧校准与反馈闭环

2026-10-15 与用户确定的口径：

| 级别 | 含义 | 门槛 |
| --- | --- | --- |
| **错误** | 交付前必须处理（占位符损坏、型号/代码丢失、整段未翻） | 漏报必须为 0，误报不超过 2% |
| **需确认** | 系统无法判断（重译收敛后仍不变、模型保留了无法归类的内容） | 不自动重译，列在报告中 |
| **已保留** | 按策略保留原文（公司名、地址块等） | 不报错，只列出 |

每次改规则都要在样本集上同时看误报和漏报：两者任何一项变差都不能合并（`npm run test:rule-golden` 与基线比较）。

v0.3.2 补了一轮“漏报”样本（审查中发现的 91 条：含公司名的整句中文未翻、普通英文词未翻、11 个以上占位符恢复错位、`SpO2`/`HbA1c` 等代码被拆开或丢失）。在 652 条样本上：旧代码误报 3 / 漏报 34，新代码 0 / 0。

反馈闭环（“确认无误”如何变成规则）：

1. 报告中点“确认无误”后，该条不再报错，但会列在“已确认无误”里，标为 **待审核**，可随时撤销；质量报告文本和导出栏都会提示还有几处待审核内容。
2. 确认的键包含原文哈希：同一译文出现在别的原文下仍会被检查，避免一次点击放过不相关的句子。
3. 确认记录通过 `/api/qa-feedback` 存到 Cloudflare KV（绑定名 `QA_FEEDBACK`，只存确认的短文本），公司电脑和 Mac 共用；未配置绑定时自动只存在浏览器里。
4. 维护者运行 `npm run qa-feedback:pull`，把未审核的确认写成 `local-data/qa-feedback/candidates-<日期>.jsonl`；逐条审核后，正确的追加到 `fixtures/rule-golden-captured.jsonl`，跑 `npm run test:rule-golden`，再运行 `npm run qa-feedback:mark-reviewed`，网页上的“待审核”标记随之消失。
