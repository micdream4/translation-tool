# 翻译项目复盘与避坑指南（DOCX/Excel）

## 1. 目标
沉淀本项目在“文档翻译 + 原格式回填”中的关键经验，避免后续项目把优化重点放错方向。

## 2. 核心结论（最重要的两条）

### 2.1 先定义问题维度：模型问题 vs 工程问题
在翻译链路里，必须先判断问题属于哪一层：

1. 模型问题：术语误译、语义偏差、风格不一致。
2. 工程问题：分段切分错误、占位符处理错误、回填破坏 run/样式、段落合并丢空格、标点粘连。

本项目的主要故障（粘词、占位符残留、格式异常）以工程问题为主，不是模型能力不足。  
如果一开始误判为模型问题，就会浪费时间在“换模型/调 prompt”，但无法解决回填后文档质量问题。

### 2.2 确定正确技术方案：按语义切分，不按固定长度切分
Excel 可以天然按单元格/行处理；DOCX 不能直接套用固定长度切分。  
DOCX 必须按语义边界切分（句子、段落、列表项、表格单元语义段），否则高概率出现：

1. 单词被截断后回拼，导致 `AnalyzerThe`、`withGB/T`、`93%below` 这类粘连。
2. 缩写和术语与前后词粘连（`WBC`、`RBC`、`USB` 等）。
3. 占位符错位或残留（`TKN_0`、`__ID_0__`）。

结论：先做“语义切分 + 稳定回填”再谈模型优化，收益最大。

## 3. 配套工程原则（支撑核心两条）

1. 回填优先级高于翻译速度：不破坏原文档样式、图片、分页、表格结构。
2. 占位符必须“冻结-翻译-还原”全流程闭环，且可审计。
3. 术语、品牌名、型号、标准号必须支持保护词机制（Do Not Translate）。
4. 质量检查用于“发现问题 + 提示重试”，默认不应无限制阻断下载。
5. `Retry Missing Segments` 必须只重试异常段，不能触发全量重跑。
6. Pause/Resume 必须是真断点续跑，不能回到起点。

## 4. 推荐处理流程（面向上线版本）

1. 上传文档后先做结构解析和语义切分。
2. 对品牌名/术语/占位符做预保护。
3. 分批翻译并立即局部回填。
4. 翻译完成后自动审计：源语言残留、占位符残留、粘词/空格异常。
5. 用户可点 `Retry Missing Segments` 重试异常段。
6. 提供 `Export Issue Report` 导出问题段清单。
7. 允许下载，但在有异常时给出明确风险提示。
8. 用户下载后可抽检关键页（封面、目录、表格页、图注页、术语密集页）。

## 5. 给后续项目的落地建议

1. 先做一份“问题分类表”（模型/工程）再排期。
2. 把“语义切分 + 回填稳定性”列为第一里程碑。
3. 测试样例必须覆盖：长文档、表格、编号列表、混合中英、占位符、缩写密集页。
4. 验收标准要包含“可发布文档质量”，不仅是“翻译完成率”。

## 6. 已知风险记录

### 6.1 Excel 解析库 `xlsx` 的安全公告

当前项目仍使用 npm 包 `xlsx` 做 `.xlsx` 解析与写回。`npm audit --omit=dev` 会报告 `xlsx` 存在 high 级别公告，且当前 npm 上没有可自动修复版本。

短期缓解：
1. 已禁用旧 `.xls` 上传，只允许 `.xlsx`。
2. 工具按内部可信文件场景使用，不建议开放给匿名外部上传。
3. 文档中明确记录该风险。

后续彻底方案：
1. 评估迁移到维护更活跃的 Excel 解析/写回库。
2. 或把 Excel 解析放到服务端隔离环境，降低恶意文件对浏览器端的影响面。

### 6.2 PDF 上传翻译可行性评估

当前版本已支持第一阶段 PDF 上传：文本型 PDF 会通过 `pdfjs-dist` 抽取可复制文本，按页/文本段走现有模型翻译流程，并导出为仅含译文的 Word `.docx`。PDF 中可提取的图片会按页插入到对应译文段落后。上传白名单为 `.xlsx,.docx,.pdf`。

第一阶段仍不承诺扫描件 OCR、图片内文字翻译或 PDF 原版式坐标重建；上传后如检测到图片对象，会显示已回填图片数量和范围提示。

PDF 可以分三档支持：

1. **文本型 PDF，输出译文 Word**
   已实现。解析 PDF 文本后按页/段落送翻译，导出 `.docx`，并回填可提取图片。优点是快、风险低、方便编辑；缺点是不保留原 PDF 坐标级版式，也不处理图片内文字。

2. **文本型 PDF，生成“覆盖式”翻译 PDF**
   中等可行。需要记录文字坐标，在原页上遮盖源文字并绘制译文。难点是中文/多语字体嵌入、换行、表格、分页和文字长度变化。适合表格少、版式简单的 PDF，不适合复杂说明书直接承诺 1:1。

3. **扫描件/图片型 PDF + OCR + 回填**
   工程量最大。需要 OCR、版面分析、表格检测、图片文字定位和人工校验。更适合服务端 pipeline，不建议先放到当前浏览器端主流程。

后续路线：
1. 对 PDF 文本分段增加更细的段落/表格识别，减少异常换行。
2. 对纯扫描件提示 OCR 入口或服务端 OCR pipeline。
3. 等文本型 PDF MVP 稳定后，再评估图片文字 OCR、坐标覆盖式 PDF 导出。

---

这份文档用于约束后续同类项目的技术路线：  
先把问题定义清楚，再用正确切分方案实现稳定回填，最后再做模型层优化。
